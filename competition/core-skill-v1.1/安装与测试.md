# 出海资料预审核心 Skill：安装与测试

## 这一包是什么

这是一套在现有 ChuHai-agent 中验证业务闭环的配置材料，未修改应用源码、未自动安装到运行实例、未替换现有智能体。所有准备文件均位于 ChuHai-agent/competition/core-skill-v1.1。

- `export-document-review.zip`：上传这个完整ZIP，含根说明、参考约定和Python标准库模板脚本。
- `export-document-review/SKILL.md`：核查与补件复核操作规范。
- `系统提示词.txt`：单独复制到测试智能体的系统提示词设置。
- `本地验证记录.md`：包与模板脚本的验证结果。不是实际智能体效果测试。

本 Skill 不包含法规原文、不包含企业PDF、不包含小熊案例标准答案。继续选择你已经建好的真实知识库，上传你此前的测试文件。后续改Skill后需要重新打包上传或通过共享Skill在线编辑；仅修改此处磁盘文件不会自动更新已安装版本。

## 一、安装 Skill

1. 浏览器打开现有 **http://localhost:25173**，登录 ChuHai-agent。不要启动原 YUXi 服务。
2. 进入 **扩展 → Skills → 上传**，选择本目录的 `export-document-review.zip`。不要只上传单个 SKILL.md，否则会缺少模板脚本与参考文件。
3. 预览安装草稿，核对名称“出海资料预审”、slug `export-document-review`、版本1.1.0，文件清单含 `references/` 和 `scripts/render_review.py`。
4. 使用有管理权限的账号，安装到**共享来源**；读取/管理范围先只给实际测试人员，并确认启用。个人来源不解析平台依赖，首次测试优先使用共享来源。
5. 核对依赖：工具 `ocr_parse_file`、`present_artifacts`、`ask_user_question`；Skill `knowledge-base`。知识库Skill本身要可访问且已启用。不要同时安装同slug的个人版，个人版会覆盖共享版。

无需修改内置Skill目录，无需重启Docker。上传成功代表“已安装”，还要完成下一节才代表“智能体会使用”。普通账号无法安装共享版时，使用现有管理员账号完成；不要为了本次测试改应用权限代码。

## 二、配置一个独立测试智能体

1. 在当前智能体管理/配置界面，新建一个测试智能体，名称如“链证出海—核心闭环测试”，使用现有已能解析文件和检索知识库的模型与运行配置。保留原智能体用于对照。
2. 把本目录 `系统提示词.txt` 的全部内容复制到系统提示词栏，**替换**旧的“儿童毛绒玩具预审助手”提示词；不要把两份指令首尾拼接。
3. 在知识库选择中选现有欧盟玩具法规与官方指南知识库。仅有Skill不会自动得到知识库权限；不要只上传法规PDF到聊天而漏挂知识库。
4. 在 Skills 选择中选“出海资料预审”和 `knowledge-base`。在**预加载**选择中选“出海资料预审”；系统会展开其Skill依赖。其他Skill按需保留，首次无需全部预加载。
5. 保留当前可用的文件读写、文件搜索和沙盒执行能力，让智能体能读取parsed_path、写result.json并执行Python模板。Skill声明的工具依赖不代替沙盒文件权限；不要为了测试放开全磁盘权限。
6. 保存，开启**新的对话/测试项目**。已开始运行的任务不会自动换成新配置。先做下面的配置检查，不使用旧对话的结论当证据。

配置检查消息：

```text
请读取 当前已选的1.1.0版出海资料预审Skill 和它的两个references文件，确认核心Skill是否可加载、knowledge-base依赖是否可用、模板脚本是否存在，以及本次工作目录是否可读写和执行Python。只核实配置，不做预审，不修改旧文件。报告实际检查结果；不能调用的能力明确指出。
```

通过标准：能看到真实Skill加载/文件读取记录；确认脚本路径与工作区可用。单纯回答“我具备这些能力”不算通过。核心Skill找不到时先检查启用、共享范围、Agent选择与同名个人覆盖，不先改代码。

## 三、第一轮真实文件测试

用你已经准备的测试材料：

- MO6738_EC_declaration.pdf
- MO6738_EN71_test_report.pdf
- MO6738_material_declaration.pdf
- 01_核查委托单.md（模拟内部业务背景）
- 02_拟上线文案_模拟待审.md（模拟内部待审文案）

PDF上传为原始附件；不要仅把平台截短的自动解析结果复制给模型。文件名不同可以正常使用，不要求为匹配Skill改名。如果系统限制单文件体积，先按现有可用Project文件方式放入工作区并告知实际路径，不丢掉报告后段。

发送：

```text
请使用“出海资料预审”Skill处理本次附件。
业务背景以核查委托单为准。目标是向德国客户提交资料前，核对这些文件是否对应本产品、信息是否一致、内部文案是否有证据支持，以及本次范围内还需确认什么。
两份MD是模拟内部文件，其余PDF是公开供应商资料；不要把模拟文案问题归因于真实厂商。
请实际查询挂载知识库；依据缺失时明确范围限制。完成首次预审，生成v1结构化记录、可视化看板、核查清单、分对象补件请求和文案修订建议。先给我三件最该做的事，不在聊天重复全文。
```

通过标准：

1. 按委托单识别产品、市场、日期，不重复问已知信息；未知角色保留未知。
2. 实际解析PDF后继续读取保存的全文/分段，实际检索并打开知识库内容。前端短预览截断不能作为已读全文的依据。
3. 发现来自文件核对；事项有稳定ID、两种状态、证据上下文和下一步。报告多型号对应关系不混淆；不能定位页码就直说。
4. 实际生成 `result.json`、HTML看板、三份MD文件；HTML里事项数量和MD一致，证据可展开，未伪装自动发送或正式合规结论。
5. 有真实交付物卡片。若只看到HTML代码块或“已保存”一句话但没有实际文件，不算完成。HTML预览不可用时先下载浏览器打开，不能据此断定核查失败。

这一步不预设“必须找出几项”，也不能把旧截图中的结论直接抄进新记录。

## 四、补件闭环测试

### 测试A：形成可办理的补件请求

看完v1后发：

```text
请基于刚完成的记录，分别整理给供应商的补件邮件草稿和内部应修改的事项。使用原事项ID，写清需要对方提供什么，以及收到后核对什么。先展示草稿，不发送消息。
```

通过标准：外部补件与内部草稿修订分开；不能用无证据的指控；没有假称已联系供应商。无需为仅查看草稿机械创建新版本；若新增核查记录才生成新版。

### 测试B：只有口述不能关闭

选v1一个真实未解决ID，将下面Cxxx替换成它：

```text
Cxxx已经处理好了，但我现在没有新文件。请记录我的口述，并给我更新版看板。
```

通过标准：读取v1后创建v2；原ID保留、原证据保留，办理状态待复核，不能仅凭口述改为本项有支持或关闭。变化记录注明“用户口述”。v1仍能打开。

### 测试C：内部新文案与供应商新证据不同

根据第一次实际建议，人工另存一份修订文案MD上传；文件开头注明“模拟内部修订稿，仅修订文字，非供应商新材料”。不要伪造检测报告或供应商声明。

```text
这份是内部文案修订稿。请与上版记录比较，只在证据足够时更新相关事项，并检查连带影响。内部文案的改变不能证明产品成分或检测适用性。生成下一版并保留旧版本，说明哪些已复核、哪些仍需供应商或专业人员确认。
```

通过标准：该份草稿的具体文本矛盾可被证据支持地解决；无法证明的材料/测试问题保持待确认，不一起全部关闭。新增文件有来源分类，版本差异有依据。没有实际供应商补充文件时，不宣称已跑通供应商证据真实性验证。

### 测试D：有真实补充资料再复核

如能取得实际对应型号的新公开资料或供应商文件，上传后指明来源，请智能体复核相关ID。没有就保留此项未测试。竞赛模拟补件文件必须显著标“模拟”，只能验证交互流程，不能证明真实供应商已完成整改。

## 五、怎样判断下一步该优化哪里

| 现象 | 先处理 |
| --- | --- |
| 找不到Skill/工具 | 查安装来源、共享权限、启用、选择和预加载 |
| 找不到依据 | 查是否挂载正确知识库及是否有原文；不是加一句“认真核查” |
| PDF信息错列/漏页 | 查OCR全文、表格上下文与解析限制，必要时单独解析受影响页面 |
| 结论可用但回复很长 | 调整系统提示词的最终摘要规则 |
| 看板字段/计数不一致 | 查result.json和模板执行记录，别让模型另算一套统计 |
| 口述导致自动关闭 | 查Skill执行与复核依据；必要时增加应用端状态约束 |
| HTML有文件但无法内嵌 | 下载浏览器打开验证；独立看板已可测试，嵌入体验后续改前端 |
| 想点击按钮就复核/多人分配 | 需要应用接口与持久状态支持，后续开发，不靠提示词假装实现 |

先把v1→补件草稿→口述待复核→内部修订新版本这条链跑通，再决定是否做应用界面开发。提示词和Skill能指导流程，但不能保证模型每次严格执行，也不等于后台已经有强制状态机或完整审计系统。
